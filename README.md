# Narrative domain fusion

The fusion input is exclusively the 15 local `*_domainfile.pddl` files and
their paired problems under `data/narra-domains`. The UniDomain paper and
repository provide the algorithm and prompts only; their domains are not used
as input.

## Strict UniDomain reproduction with local Ollama

Install the Python dependencies and make a local model available:

```powershell
python -m pip install -r requirements-fusion.txt
ollama pull gemma3:4b
$env:USE_TF='0'
$env:TRANSFORMERS_NO_TF='1'
python unidomain_ollama_fusion.py `
  --input data/narra-domains `
  --output data/merged_strict `
  --model gemma3:4b `
  --num-workers 4
```

This path follows the official UniDomain binary-tree procedure:
`all-mpnet-base-v2` embeddings shortlist predicate and operator candidates in
descending cosine-similarity order at threshold `0.3`, then the local LLM
verifies predicate merges before operator merges. The three domain-fusion
prompts are copied unchanged from the official repository.

The local narrative PDDL files do not contain the natural-language predicate
descriptions expected by UniDomain atomic-domain JSON, so this adapter derives
descriptions from declarations and action usage. Ollama's JSON-schema response
format is also retained as a provider-level adaptation. There is no secondary
repair prompt or local semantic override of the LLM merge decision.

Strict artifacts are written to `data/merged_strict/`:

- `meta_domain.pddl`: final fused domain.
- `meta_domain.json`: counts, source-to-final mappings, and merge decisions.
- `problems/`: the 15 problems rewritten for the fused domain.
- `domain_fusion/`: leaf and intermediate binary-tree nodes.
- `fusion_tree.json`, `mapping_table.json`, and `validation.json`: provenance
  and validation metadata.

Any existing `data/merged_strict` directory may have been generated by an
earlier workflow and must be regenerated after alignment changes. The final
`validation.json` checks PDDL structure and rewritten problem references; it
does not by itself prove that every LLM merge is semantically correct.

Run the tests with:

```powershell
python -m unittest discover -s tests -v
```

## Deterministic offline fallback

`merge_domains.py` remains available when no embedding model or LLM is
available:

```powershell
python merge_domains.py
```

It writes to `data/merged/` and uses reviewed, dataset-specific semantic groups
instead of the paper's embedding-plus-LLM candidate verification. It is useful
as an offline fallback but is not the strict UniDomain reproduction.
